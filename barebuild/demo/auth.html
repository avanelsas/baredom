BareBuild — credentials

The same projection as the other demos, behind a bearer token. A static header is declared on the element, the rotating credential is attached by a decorator at the edge, and a refused credential arrives as a failure the consumer decides what to do about.

What actually went over the wire

One line per request, written by the decorator itself as it attached the credential, paired with what the server answered. Nothing here is narrated by the page, which is why an accepted read shows no status: a non-2xx becomes a failure before the envelope is ever read, so success implies a 200 rather than reporting one.

What each part is doing

headers declares a static header, read once when the element connects. It is a fact about the resource, so it lives on the element and it shows up in the BareReplay trace alongside the request.

The decorator attaches the bearer token. A credential that refreshes on its own schedule is not a fact about the resource at any moment, so it lives at the edge instead. It runs after step, on the request step already produced, which is why the token never appears in the trace. Open the BareReplay dock and compare: the static header is recorded, the token is not.

credentials is set to same-origin here, which is the browser default. It is a straight pass-through to fetch, so there is nothing of BareBuild's to observe in it. Cookie auth would use include and needs the server to answer with a concrete Access-Control-Allow-Origin, which this dev-server does not do.

Expire the token makes the next request carry a credential the server refuses. The 401 never reaches envelope parsing: it arrives as a network failure carrying {:kind :http-status :status 401}, and this app answers it by offering re-authentication. BareBuild does not retry for you, and does not decide what a 401 means. The table empties, because rows the server will no longer serve have no business staying on screen, and the log gains a 401 refused line naming the credential that was turned away.

Re-authenticate mints a fresh token and asks again. The log gains a 200 accepted line carrying the new credential, so the rotation is visible rather than claimed.

Refresh, and the asking-again that the other two buttons do, is a submit-refresh!. A read follows an intent patch only when the intent moved, and "ask the same question again" moves nothing, so it is its own event rather than a query field invented to force a change. Watch the address bar: it stays exactly as it was. The URL is a projection of what the read is about, and a retry is not about anything.
